Target: docs/leaderboard.qmd, “Full Period” tab, the existing metrics table (chunk starting docs/leaderboard.qmd#L52). Not a new dashboard. Grep confirms zero references to detection anywhere under docs/*.qmd today – the columns exist on the leaderboard target (detection_min_n_years, detection_underpowered, and their _mt variants) but have never been rendered on any dashboard. This is exactly column-60-of-61 as #726 describes it, except currently it is column none-of-61 – the table this prototype clones does not select the detection columns at all. leaderboard.qmd is also where SSR, Credible, and Redundant already live using the identical hidden-sort-rank badge pattern this prototype reuses (see Step 3).

A NEW dashboard is not justified: the rule’s default is to extend, and this output belongs beside the Sharpe it qualifies – moving it anywhere else recreates the “column 60 of 61” problem in a different location.

This table sits beside, and must stay consistent with:

  • Credible / Redundant (same table, docs/leaderboard.qmd lines ~86-125) – both already use the exact pattern this prototype copies: a dplyr::case_when() producing a display string plus a hidden .xxx_rank integer column so DT’s default alphabetical sort doesn’t scramble assessed-good / assessed-bad / never-assessed ordering. Detection follows the same shape (.det_rank); Rigour intentionally does not need a separate rank column because its four states already sort in a sensible default order for this prototype’s purposes.
  • Strategy naming (strategy-name-consistency): the strategy column values (“OLMAR-1”, “Avoid Worst”, “Value (HML)”, …) are used unchanged – no new naming is introduced.
  • Captions (visualization-standards family): the caption is assembled dynamically from the live data (counts, not hardcoded numbers) exactly like the real table’s flag_note / bias_note / gross_note / cost_note / diversification_note blocks.
  • Table styling (dashboard-table-styling): no inline width:100%; badges are inline <span> elements inside a cell, which keeps the table shrink-to-content and right-justified per the existing global CSS.
  • Deflated Sharpe tab (docs/leaderboard.qmd, “Deflated Sharpe” tab, strat_deflated_sharpe target): the Rigour badge summarises exactly the three columns (deflated_sharpe, dsr_pvalue, k_eff_leaderboard) that tab already renders in full for the strategies it covers – see Step 5 for the resulting consolidation proposal.

Four defences, none of them relying on the reader noticing a colour:

  1. Structural adjacency. Detection is the column immediately right of Sharpe – not reachable only by scrolling past 50 other columns, which is documented as the actual mechanism of the original failure (#726: “the metric had existed as leaderboard column 60 of 61 and had never been read”).
  2. Every state carries a distinct symbol AND a text label, not colour alone (✓/⚠/–/✗ plus “Detectable” / “Underpowered” / “n/a” / “NOT COMPUTED”) – satisfies colour-blind accessibility and dark/light contrast simultaneously.
  3. A always-visible summary callout above the table, in the same visual register as the existing ::: {.callout-warning} survivorship-bias block at the top of leaderboard.qmd – the project’s own established pattern for “this caveat is load-bearing, not decoration.” It states the counts in prose, dynamically computed, every render – a reader who never hovers a badge still reads “6 of 8 strategies are underpowered.”
  4. Every amber/red badge links to the tracking issue (#726 or #728) in its tooltip – “acknowledge” has a concrete next action (read the issue, or close it once the underlying gap is fixed), not just a colour a reader learns to filter out.
Proposal: fold “Deflated Sharpe” from a standalone tab into a Rigour detail expansion on the main ranking table, once this Phase 0 design is built for real.

Today docs/leaderboard.qmd has a “Deflated Sharpe” tab (strat_deflated_sharpe target) that exists solely to show the same three numbers (deflated_sharpe, dsr_pvalue, k_eff_leaderboard) this prototype’s Rigour badge already summarises inline, for the same set of strategies. With coverage now at 11 of 17 (up from 4, per #728 items 1-2, landed concurrently with this dispatch) the standalone tab is close to covering the same footprint as the main table anyway. Once Rigour ships with a working tooltip/expand-row showing the three numeric values on demand (DT’s render = "expand" column pattern, no new tab needed), the “Deflated Sharpe” tab’s unique remaining value is near zero and it should be retired, folding its content into a badge hover/expand on the ranking table. This is a genuine simplification, not a relabeling: one fewer tab, zero lost information (the exemption reasons and numeric values both survive as tooltip content), and the information moves from a separately-navigated tab to the same row as the Sharpe it qualifies – consistent with the requirement 2 in the detection-power-required rule (“beside its Sharpe, not in a distant column”), which applies equally to rigour metrics per #728 item 3’s framing of the same defect one layer up.

Net effect on docs/DASHBOARDS.md inventory: dashboard count unchanged (11), tab count within leaderboard.qmd reduced by one once implemented. This is a smaller consolidation than a dashboard merge, but it is concrete, and “no change” was not available as an honest answer – the Deflated Sharpe tab’s argument for existing separately gets weaker every time rigour coverage widens, which is exactly what is happening in this repo this week.
