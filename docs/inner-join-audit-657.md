For each row I read the join line plus 15 to 30 lines of context and asked:

1. **Unmatched rows.** Which side's unmatched rows are dropped, and could that be a whole calendar period shared by every constituent series (the #641 hazard) or only one instrument-period?
2. **Key type.** Could `Date` vs `POSIXct`, character vs factor, whitespace or case make the join empty or partial **without an error**? (`dplyr` 1.1 errors on character vs `Date`; it does not error on `Date` vs `POSIXct`, which coerce.)
3. **Guard.** Is there a post-join row-count assertion, a warning with a count, or a self-reported `n`?

### Verdicts

- **SAFE**: one of (a) loss cannot occur by construction (fixed enumeration, self-join, key set equal on both sides by lineage), (b) the drop is intended and bounded to the series edge, (c) a guard or self-reported `n` makes any loss visible, (d) measured at zero mid-series loss in the 2026-09-24 audit **[M]**, or (e) the code is unreachable from any `_targets.R`.
- **AT-RISK**: structurally capable of silently dropping a period (or pairing the wrong objects) and no guard makes it visible. This is NOT a claim that loss currently happens; it is "unmeasured and unguarded".
- **INDETERMINATE**: I could not tell from the code. The row states the read-only query that would decide it.

Where I use "overlap window" I mean the #657 definition: the calendar range from `max(min key of x, min key of y)` to `min(max key of x, max key of y)`. A join drops a period **inside the overlap window** only if the key is missing on one side while present on the other's range. Months before the later series starts or after the earlier one ends are edge effects, not defects. A decider query below that says "drops inside the overlap window" means: `setdiff(months in the overlap window of x and y, months in the result)`.

## Proposed guard (design only)

A reusable helper so each period-keyed join states its expectation and reports the result, instead of each file hand-rolling `setdiff()` and a `cli_warn()` as `.warn_ltr_join_gap()` does. Not implemented; nothing under `R/` was touched.

```r
hd_checked_join(
  x, y, by,                       # character vector of key columns; same names on both sides
  label,                          # e.g. "strat_returns_aligned: family x ltr"
  how = c("inner", "left", "full"),
  allow_edge_loss = TRUE,         # unmatched keys outside the overlap window are reported, not failed
  max_lost_inside_overlap = 0L,   # keys inside the overlap window absent from the result
  unique_keys = TRUE,             # require at most one row per key on each side
  on_violation = c("abort", "warn")
)
```

Returns the joined tibble with attribute `join_coverage`, a list holding: `label`, `n_x`, `n_y`, `n_out`, the overlap window `[lo, hi]`, `lost_x_inside`, `lost_y_inside` (vectors of keys), `lost_x_edge`, `lost_y_edge` (counts), and `duplicated_keys`. The caller can pass the attribute through to a `join_n` column or a caption so the count is published, which closes the #657 "dropped-month count reported" item for the correlation targets.

Three outcomes, mirroring the repo's 0 / 1 / 3 convention (`checks-must-distinguish-unknown`):

| Outcome | When | Signalled as |
|---|---|---|
| **PASS** | Keys comparable; at most `max_lost_inside_overlap` keys lost inside the overlap window; no duplicated keys when `unique_keys`; edge loss reported only | returns normally, attribute attached |
| **FAIL** | More keys lost inside the overlap window than allowed, or duplicated keys fan out the result | condition class `hd_join_coverage_error`, subclass of `rlang_error`; with `on_violation = "warn"` it is a `hd_join_coverage_warning` instead. The message lists the lost keys (first 10 plus a count) |
| **INDETERMINATE** | The check cannot decide: key classes differ in a way that coerces silently (`Date` vs `POSIXct`, character vs factor), either side has zero rows or an all-`NA` key, keys are not orderable so no overlap window exists, or fewer than two distinct keys | condition class `hd_join_coverage_indeterminate`, always an abort, never reported as PASS. The message says *why* it could not decide |

Design notes:

- The overlap window is computed from the keys themselves, so the helper uses the exact-window definition from the #657 issue and does not overstate the hazard for series with intentionally different start dates.
- `Date` vs `POSIXct` is INDETERMINATE rather than FAIL because the right fix (coerce which side?) is the caller's decision. This is the one case `dplyr` joins without an error.
- Falsification of the helper before first use (`verification-before-completion`): a test that removes one mid-series month from `y` must produce FAIL; a test that shifts `y`'s start later must still PASS; a test with `Date` vs `POSIXct` keys must produce INDETERMINATE. A helper that cannot go red is not a check.
- Adoption order: A10 (`hd_factor_null_test`, add `n_obs` and the attribute), A9, A8, A6/A7, B3, then the rest of the AT-RISK and INDETERMINATE rows. SAFE rows with their own guard (A1, B18, B19) keep it.

Lint-style detection of new period-keyed joins (the last #657 item): an `ast-grep` or regex rule flagging `inner_join(..., by = "ym" | "date" | "year_month")` in `R/**` and `packages/*/R/**` that is not on an allow-list whose every entry carries a reason (the same discipline as `dynamic-prose-values`). The rule only reports the shape; separating CONFIRMED from BENIGN still needs the decider queries. A drift test comparing the G1 count (61 live lines) with this census would force an update to this document whenever a join is added; I did not add one, because root tests run only in local `verify.sh` and a count test would fail every unrelated PR that adds a join.

### Guard
